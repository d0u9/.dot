# Zsh completion design

## Status

This document is a proposal for extending command completion in this dotfiles
repository. It describes the intended design; the completion registry and
management commands below have not been implemented yet.

The current configuration already initializes Zsh's native completion system
with `compinit` in `core/shell.zsh`. The goal is to build on that mechanism
without bringing back Oh My Zsh or adding a plugin manager solely for
completion.

## Goals

- Support macOS and Linux without assuming that the same tools or versions are
  installed on every host.
- Keep shell startup fast: an external CLI must not run every time Zsh starts.
- Let Zsh autoload completion functions when completion is first requested.
- Make support for a command easy to add, inspect, refresh, and remove.
- Generate completion from the executable installed on the current machine, so
  it stays compatible with that machine's CLI version.
- Keep generated, machine-specific files out of the public repository.
- Preserve the existing public pre/post hooks and disconnected private
  `host-conf/` entry point.

## Non-goals

- Reimplementing Zsh's completion system.
- Loading an Oh My Zsh plugin just to obtain one completion function.
- Wrapping commands such as `docker` or `kubectl` merely to delay setup until
  their first execution.
- Automatically installing every supported CLI.
- Supporting a `$HOME` shared between hosts of different platforms. The
  generated files live under `$HOME` and are keyed by nothing but the command
  name, so two hosts sharing a home directory over NFS would overwrite each
  other's completion. Add the platform to the cache path if that ever becomes
  a real configuration.

## Three kinds of command support

### 1. Native or package-provided completion

Zsh completion functions use filenames such as `_git`, `_docker`, and
`_kubectl`. When their directory is in `fpath`, `compinit` registers them and
Zsh autoloads the function when the user first requests completion.

This is already the desired form of on-demand loading. If Zsh or the operating
system package supplies a suitable completion, no repository-specific setup is
needed.

Examples:

- `_git` shipped with Zsh
- completion functions installed into a system `site-functions` directory
- completion functions installed by Homebrew or a Linux package

This is also the cheapest work available, and it should come first. Homebrew
installs the completions shipped by docker, kubectl and gh into
`$HOMEBREW_PREFIX/share/zsh/site-functions`, and Linux packages use
`/usr/share/zsh/site-functions` or `/usr/share/zsh/vendor-completions`. Adding
those directories to `fpath` before `compinit` covers a large part of the
motivating problem on a normal Homebrew or apt host, with no registry, no
generated files and nothing to refresh. Only what remains uncovered justifies
the machinery below.

### 2. Completion generated by a CLI

Many modern CLIs can print a completion function:

```text
docker  -> docker completion zsh
kubectl -> kubectl completion zsh
helm    -> helm completion zsh
gh      -> gh completion -s zsh
```

These commands should run during installation or an explicit refresh, not on
every shell startup. Their output should be stored as `_command` files in a
completion cache that is added to `fpath` before `compinit` runs.

Docker documents this `fpath` approach for installations without Oh My Zsh:
<https://docs.docker.com/engine/cli/completion/>. Kubectl likewise supports
writing `kubectl completion zsh` to an `_kubectl` file:
<https://kubernetes.io/docs/reference/kubectl/generated/kubectl_completion/>.

A generated file is only useful once it is also associated with the command.
Most of these generators emit `#compdef NAME` as their first line, which is
what makes autoloading work, but not all of them do; some versions instead
expect the caller to append `compdef _kubectl kubectl`. A file that loads but
never associates fails silently -- the file looks correct and Tab does
nothing -- so the registry needs a per-entry way to say what a generator's
output still needs. See the registry section.

### 3. Interactive shell integration

Some tools do more than complete arguments. They install widgets, hooks, or
shell functions and therefore belong in `core/integrations.zsh`, not in the
completion registry.

Examples:

- zoxide defines `z` and `zi` and records directory changes.
- fzf installs ZLE widgets such as the `Ctrl-R` history search.
- direnv installs a directory-change or prompt hook.
- atuin can replace Zsh's history search behavior.

Each integration should remain optional and be guarded by the presence of its
command.

## Proposed layout

Tracked public configuration:

```text
apps/zsh/
├── doc/completion.md
├── bin/zsh-completion
└── core/
    ├── shell.zsh
    ├── completions.zsh
    ├── aliases.zsh
    ├── integrations.zsh
    └── plugins.zsh
```

Generated host-local state:

```text
${XDG_CACHE_HOME:-$HOME/.cache}/zsh/
└── completions/
    ├── _docker
    ├── _kubectl
    └── _helm
```

Responsibilities:

- `core/completions.zsh` adds the system `site-functions` directories and the
  generated directory to `fpath`, runs `compinit`, defines completion styles,
  and maps completion for aliases where necessary.
- `bin/zsh-completion` contains the registry and the commands used to generate
  and maintain cached completion files.
- `core/integrations.zsh` continues to own tools that modify the interactive
  shell beyond completion.
- `apps/zsh-install.sh` invokes a non-interactive completion refresh after the
  rest of the Zsh installation has succeeded.

The generated completion directory must be added to `fpath` before `compinit`.

The registry is a standalone script rather than a file sourced at startup.
Sourcing it would parse a few hundred lines in every interactive shell to
define a function that is called a few times a year, and the installer needs
to run it from Bash anyway. An autoloaded function placed in `fpath` would
also work; a script is simpler and has one caller shape instead of two.

`core/completions.zsh` is extracted from the completion section that
`core/shell.zsh` owns today. That section also creates the cache directory and
tracks a compiled `zcompdump`; both move with it.

## Registry and management interface

The registry should be declarative: one entry identifies the command, how to
ask it for Zsh completion, and what its output still needs before it will
associate. Conceptually:

```text
docker  | docker completion zsh   |
kubectl | kubectl completion zsh  |
helm    | helm completion zsh     |
gh      | gh completion -s zsh    | compdef _gh gh
```

The third field is empty for a generator that already emits `#compdef`. It
exists because that is the failure mode that cannot be detected by inspecting
the file's exit status or size.

The user-facing interface should start small:

```text
zsh-completion refresh
zsh-completion refresh docker
zsh-completion remove docker
```

Expected behavior:

- `refresh` updates every installed registered command and skips missing ones.
- `refresh NAME` updates a single command and returns an error for an unknown
  registry entry.
- `remove NAME` deletes only that command's generated completion.

`list` and `doctor` are deliberately left out of the first implementation.
`doctor` in particular -- checking `fpath`, cache permissions, filenames and
the association reported by `_comps` -- is a substantial amount of code for a
diagnostic that is needed after a specific failure, and the shape of that
failure is not known yet. Add them when something has actually gone wrong and
the check can be written against the real symptom.

Adding or removing support should normally require changing one registry entry,
not editing startup control flow.

## Refresh and version handling

Completion must be generated by the executable currently resolved on the host.
This matters when, for example, macOS and a Linux server use different kubectl
or Docker versions.

Provenance belongs in the generated file itself, as a header comment beneath
the `#compdef` line: the resolved executable path, the version string it
reported, the generator definition used, and the time of generation. This
replaces a parallel metadata directory that would have to be kept in step with
the completion files and cleaned up alongside them; `remove` becomes one
`rm`, and a file that is inspected by hand explains where it came from.

Freshness should be decided on the version string rather than on the
executable's modification time and size. A Homebrew reinstall of the same
version changes mtime and size while producing identical completion, and a
package upgrade that matters always changes the version. `refresh` therefore
runs `NAME --version` (cheap, one fork per registered and installed command,
and only during an explicit refresh or installation) and regenerates when it
differs from the recorded value, or when the file is missing. A forced refresh
flag covers a CLI that changes its completion output without changing its
version.

`refresh` should skip a command whose completion function is already reachable
through `fpath` from a system or package directory, unless forced. Maintaining
a second, generated `_docker` that shadows the one Homebrew installed and
updates is work with no return.

Generation should be atomic:

1. Generate into a temporary file in the destination directory.
2. Reject an empty result or a failed generator command.
3. Run `zsh -n` against the generated file.
4. Apply the registry entry's association fixup, if any.
5. Rename the valid temporary file over the previous cached file.
6. Invalidate the completion dump (see below).

This keeps the last known-good completion when generation fails. Step 3 is not
optional. A CLI that prints a usage message or an error page to stdout
produces a non-empty file and a zero exit status often enough that size and
status alone do not distinguish success from garbage; parsing does.

The cache directory must be created with a mode that `compinit`'s security
check accepts. A group-writable or world-writable directory in `fpath` makes
`compinit` refuse to load anything from it and prompt about insecure
directories, which looks like a completely different failure. Create it `755`
(or `700`) explicitly rather than relying on the ambient umask.

## Invalidating the completion dump

`core/shell.zsh` caches `compinit`'s dump and, for up to a day, starts with
`compinit -C`, which skips both the security check and the staleness
comparison. A newly generated `_docker` placed into a directory already in
`fpath` is therefore invisible to new shells until that window expires.

`refresh` must delete the dump and its compiled `.zwc` after installing any
completion file. Without this, the normal experience of installing a CLI and
running a refresh is that completion does not work, for reasons that have
nothing to do with the file just written. This is a required step, not a
cleanup detail.

## Startup and on-demand behavior

Normal shell startup should only:

1. Add the system `site-functions` directories and the generated completion
   directory to `fpath`.
2. Initialize `compinit`, normally using its existing cache.
3. Register any explicit alias-to-command completion mappings.

It should not execute `docker`, `kubectl`, `helm`, or similar commands.

Wrapping a command to initialize completion on its first execution is avoided.
Such wrappers can alter command lookup, interfere with `command docker`, and
surprise scripts or diagnostic tools. More importantly, execution of the
command does not require completion. Zsh's native autoload behavior already
provides the useful boundary: load the completion function when the user first
presses Tab for that command.

## Aliases

An alias does not always inherit the completion association of its target. A
short alias should therefore declare the mapping explicitly after `compinit`:

```zsh
alias k=kubectl
compdef k=kubectl
```

The alias remains owned by `core/aliases.zsh`; only its completion association
belongs to `core/completions.zsh`. Removing the alias must also remove or stop
declaring its completion mapping.

## Installer behavior

The Zsh installer should create the cache directory and run the equivalent of
`zsh-completion refresh` after installing or updating optional command-line
tools. Missing commands are a normal condition, not an installation failure.
This matches how the installer already treats fzf and zoxide.

The installer should report generation failures per command while continuing
with unrelated completions. A failure should only make the overall Zsh install
fail if the requested operation explicitly requires that completion.

An explicit refresh command remains necessary because Docker, kubectl, or
another CLI can be upgraded independently of this repository's installer.

Generated completion lives under `XDG_CACHE_HOME` because it can be rebuilt
from the installed CLIs. That also means clearing the cache silently removes
completion until the next refresh; `zsh-completion refresh` is the documented
way to get it back.

## Plugin manager decision

A plugin manager is not needed for this design. `fpath`, `autoload`, and
`compinit` already provide discovery and lazy loading. A plugin manager would be
worth reconsidering only if the configuration later accumulates many
third-party Zsh plugins with independent update requirements; command
completion alone is not enough reason to add one.

## Suggested implementation sequence

1. Extract the existing completion setup from `core/shell.zsh` into
   `core/completions.zsh` without changing behavior.
2. Add the system `site-functions` directories to `fpath` before `compinit`,
   and check how much of the motivating problem is already solved.
3. Add the host-local completion cache to `fpath` before `compinit`.
4. Implement `bin/zsh-completion` with `refresh` and `remove`, including dump
   invalidation and `zsh -n` validation.
5. Register Docker and kubectl as the first two generated completions.
6. Update `apps/zsh-install.sh` to refresh installed registered commands.
7. Add `list`, `doctor`, and alias mappings only when they are needed.

## Acceptance criteria

- Starting a new interactive shell does not execute a registered external CLI.
- A generated completion is loaded only when completion for that command is
  requested.
- A completion generated by `refresh` works in the next new shell, without
  waiting for the `compinit` dump cache to expire.
- Missing optional commands do not produce startup errors.
- A failed refresh preserves the previous valid completion file.
- A generator that prints something other than a completion function is
  rejected rather than installed.
- Running refresh after switching CLI versions regenerates the completion from
  the active executable.
- A command whose completion already comes from a system or package directory
  is not shadowed by a generated copy.
- The completion cache directory does not trigger `compinit`'s insecure
  directory prompt.
- Docker and kubectl completion work on both macOS and Linux when their commands
  are installed.
- Removing a registry entry and its cached file leaves no active completion
  association after rebuilding the `compinit` cache.
- The design does not require Oh My Zsh or a Zsh plugin manager.
